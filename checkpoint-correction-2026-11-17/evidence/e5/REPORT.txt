Change: Introduce protected AggregateCheckpointState. Checkpoint delivery installs only an authority-key-matching, correctly signed candidate with a nondecreasing prefix; equal-prefix different-root delivery is rejected. Proof verification is read-only and requires the supplied checkpoint to equal the protected checkpoint, then calls the existing verifier against that protected state. Neither a proof nor a delayed older delivery can roll back the checkpoint. Existing signature checks and recovery remain active.
The simulation's checkpoint-delivery event is distinct from the proof-response check. It represents authenticated checkpoint delivery using a fixed configured signing key; it is not a new consensus, key rotation or network installation protocol.

Validation: 20 unit tests passed: 11 original tests and 9 new tests. New tests cover a valid current proof, an authentic older covering prefix (old 2, current 4, query position 1), a noncovering prefix, wrong statement/position/root, wrong checkpoint root/shard/key/signature, a same-prefix signed fork, missing protected state, monotonically increasing installation, delayed rollback, and no pruning before valid recovery. Rejected proof checks leave protected state unchanged. The E5 simulator does not implement representation migration or metadata activation, so this is not an end-to-end migration crash/persistence test.

Actual caller regression: original simulator with protected prefix 4 and candidate prefix 1 prunes covered position 1 at 60 ms; other positions prune at valid recovery 1060 ms. Revised simulator prunes all four only at 1060 ms. Raw results are regression_before.json and regression_after.json. This is an old-authentic-checkpoint policy mismatch, not a forged block or signature.
